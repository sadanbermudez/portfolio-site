Case study

19 to 20 Oct 2026

Finding a 20x stall in a local LLM engine

My voice assistant paused about 3 seconds before every answer. The model itself was fast, so the delay had to be somewhere else. I narrowed it down one measurement at a time:

  1. Raw engine vs server. The engine alone read 16 prompt tokens in 0.11 s; the server took 1.4 to 2.5 s for the same work. The problem was server-side.
  2. Ruled out settings. Batch size, context size and slot count made no difference on a separate test server.
  3. Timestamped logs. Two snapshot saves of about 0.6 s each made up the delay. The model is a hybrid whose recurrent state must be snapshotted to resume conversations.
  4. Turned snapshots off. Voice became 15x faster, but the agent lost its cache and slowed to 21 s per turn. Reverted within half an hour.
  5. Newer build and four GPU switches. No change, so the cost was in the code, not the configuration.
  6. A first patch that failed. Skipping redundant GPU waits saved almost nothing (0.65 s to 0.61 s). Discarded.
  7. Timers on the read path. The waits took 14 ms in total. The CPU copy took 7,738 ms for 880 MB: about 114 MB/s, because the GPU memory it read is not CPU-cached.
  8. A one-condition fix. Read directly only from cached memory; otherwise let the GPU copy into a cached staging buffer first. 880 MB in 553 ms.
// ggml_vk_buffer_read_2d(): take the direct host read only when it is fast
if (src->memory_property_flags & vk::MemoryPropertyFlagBits::eHostVisible && src->device->uma &&

Verified, not assumed. At temperature 0 with a fixed seed, the fixed build gave word-for-word identical answers to the stock build, including in a mode that forces snapshot restores (4 of 4). I rehearsed the exact deployment on a copy before touching production, and kept a one-step undo.

Honest outcome. After deploying, I found that the Vulkan backend's maintainer had merged the same fix two weeks earlier (llama.cpp #30049), prompted by a benchmark on the same GPU. My engine version predated it. This is an independent diagnosis, not an upstream contribution, and it taught me to check a file's recent history before patching it.

Signature piece

photonics-lab-mcp

An AI agent that runs a physics experiment, inside safety limits it cannot override

I built an MCP server that gives an AI agent an optics bench: an 800 nm laser, a spectrometer, peak and power-law fits, and a lab notebook. The bench is a simulator with realistic detector noise and saturation; a real power-meter driver (Thorlabs PM100, SCPI) is included and tested against a simulated instrument, not yet on hardware.

The agent, a local 35B model on this laptop, got one question and no procedure: is the 1270 nm emission excited by one photon or two? The answer is hidden in the server. Signal grows as Pn, so the slope on a log-log plot gives the photon order. The agent had to plan the powers, keep the detector out of saturation, fit and conclude.

Hidden truthAgent's resultTool callsTimeVerdict
Two-photon2.004 ± 0.032891 sCorrect
One-photon (control)1.003 ± 0.0023284 sCorrect

Why the control matters. At 800 nm the textbook guess is "two-photon". The control run uses the same setup with a one-photon sample, and the agent still measured 1. It read the slope rather than reciting the expected answer.

What it got wrong. The measurements were sound; the closing physics was not. In both runs the agent confused how singlet oxygen forms: it tied the 3.1 eV of two 800 nm photons to the oxygen emission, and later described singlet oxygen as excited by absorption. In reality the sensitiser absorbs, and its triplet state passes the energy to oxygen. A reliable operator and a careless interpreter, which is why the design puts the safety limits and the statistics in the server and leaves the interpretation to a human.

  • Safety lives in the server: power cap, arm-then-emit interlock, and read-only, configure and full permission levels. Any unexpected error puts the laser in a safe state.
  • Every action, including every refused one, goes into a lab notebook the agent can read back.
  • Peak fits report the area with its uncertainty and flag saturation; the power-law fit weights each point by its error.
  • 22 automated tests, including the instrument driver against a simulated SCPI device.

How I work

A lab notebook, applied to AI systems

  • Measure firstSame scripted requests before and after every change, on the real setup.
  • Check behaviour, not only speedDeterministic A/B tests: a faster system that answers differently is a regression.
  • Test away from productionA separate server on a spare port; production changes only after approval.
  • Keep changes reversibleA backup and a one-step undo for every deployed change, written down.
  • Record decisionsWhat changed, the numbers, and what would change my mind, including the failures.
  • Be open about AI helpI design and direct; AI coding agents (Claude Code) write much of the code. I own every decision and can explain every line.
