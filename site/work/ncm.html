This page in under a minute

In plain words
Normal AI models write an answer one piece at a time, left to right. A new approach from Stanford, next-concept modelling (NCM), first writes a rough outline of the whole answer, then fills in detail in a few rounds, working on every position at once. I ran their small Sudoku model on my laptop and compared it with large chat models on the same puzzles.
Why it matters
For tasks with a clear structure, a small model that works on the whole answer at once can come close to the best general chat model at a hundredth of the time, on a laptop. Knowing when that trade is worth it is a design decision companies face every time they choose a model.
What I built
A port of the released code from NVIDIA GPUs to an ordinary CPU, with safe loading of the model files, and a benchmark harness that gives every chat model the same prompt and checks each answer against the solution.
What I measured
NCM solved 85.2% of 500 hard boards on the laptop's CPU, in about half a second per board. On the same 50 boards it solved 40. Claude Opus 5.5 solved 46 and Claude Sonnet 5.5 solved 32, each taking about 53 to 54 seconds per board.
Glossary: the technical words on this page
Parameters
The numbers a model learns. More parameters usually means a more capable but slower and costlier model.
Token
A piece of text a model reads or writes, often part of a word. A Sudoku board here is 89 tokens.
Autoregressive
Writing one token at a time, each one depending on the last. How today's chat models generate.
Diffusion language model
A model that starts from a blank or noisy answer and improves the whole of it over many rounds.
Next-concept modelling (NCM)
Generating coarse to fine: a short, rough code for the whole answer first, then longer, more detailed codes level by level, every position in a level at once.
Function evaluation (NFE)
One pass through the model. NCM solves a board in 12, one per level; a chat model needs at least one per token it writes.
Reasoning model
A chat model that writes a long hidden chain of thought before answering, which helps on puzzles but costs time.

The idea

Coarse to fine, in parallel

A tokenizer, trained first and then frozen, turns a whole answer into a stack of codes: one code at the top, then 2, 4, 6 and so on up to 89 at the bottom, one per cell and row break. Each level adds detail to the one above. The generator predicts the stack top-down. Inside a level every position is predicted at once, so a board takes 12 passes through the model however many cells are empty.

A chat model does the opposite: one token per pass, left to right, and a reasoning model writes thousands of hidden tokens before the 81 digits it is asked for. That is where the minute per board goes.

NCM's is measured the same way, one board at a time, after an 11-second one-off model load; in batches of 100 it does 0.26 s per board.

The other parallel idea

diffusion language models

Diffusion models: parallel, but only with many steps

Diffusion language models also write the whole answer at once: they start from a blank answer and improve all of it over a number of rounds, called steps. Fewer steps should mean faster answers. I ran two open ones, Dream 7B and LLaDA 8B, on the laptop's GPU and compared them with Qwen2.5 7B, the ordinary model Dream was built from, on the same question.

ModelStepsTimeThe answer

LLaDA 8B, diffusion in 32-token blocks25664 sFluent, partly wrong

The pattern is clear: with fewer steps than the answer has words, the text falls apart, and fluent text needed about one step per word, which removes the speed advantage. On this laptop the ordinary model gave a better answer 17 to 33 times sooner. One caution: llama.cpp's diffusion code is a reference implementation that redoes the whole answer at every step, so optimised diffusion serving on datacenter GPUs is much faster than this. The trade-off between steps and quality is the part that holds.

That trade-off is what next-concept modelling attacks: instead of hundreds of rounds over the full answer, a dozen levels from a one-code sketch to the full board, each level cheap because the early ones are short.

Read this fairly

What this comparison does and does not show

  • NCM is a specialist. This model was trained only on Sudoku and can do nothing else. The chat models were never trained for this task and can do almost anything.
  • So the lesson is about fit, not about which model is "better". The strongest general model was the most accurate: Opus solved 46, NCM 40, Sonnet 32. But NCM got there in half a second on a laptop CPU with 25 million parameters, against about a minute per board on a datacenter model. When a task has a fixed structure and enough examples, that is often the better trade.
  • The chat models had no tools. Given a code interpreter, any of them could write a solver. I measured what each model does on its own.
  • 50 boards is a small sample. The gaps (46, 40 and 32 of 50) are real, but the exact percentages would move with more boards. NCM's own 500-board figure is 85.2%.

Method

How it was run

  • Released weights and code from Hazy Research (MIT licence), the Sudoku easy, medium and hard checkpoints and their test boards.
  • Ported off NVIDIA GPUs. The evaluation script assumed CUDA; I made the device selectable and ran on the laptop's CPU (AMD Ryzen AI Max+ 392). The model's own results are unchanged: 99.2% easy, 97.6% medium, 85.2% hard on 500 boards each. Timings were taken on mains power.
  • Loaded safely. The original code loads model files in a mode that can run code hidden in them. I checked that every file loads in PyTorch's safe mode, switched the code to it, and confirmed that the data files contain only plain data.
  • Diffusion runs with llama.cpp's diffusion example, built with Vulkan for the laptop's Radeon 8060S: Dream 7B and LLaDA 8B against Qwen2.5 7B, all at 8-bit, greedy, same prompt and seed. Every output is kept.
  • A benchmark harness in Python that sends each board to each model, retries on rate limits, checks every answer against the solution and saves each result as it arrives.

I designed and directed this work; the port, the harness and the runs were carried out by Claude Code running as my agent.
