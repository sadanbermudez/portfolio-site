Case study · inference performance · DeepSeek V4 Flash on colibri · 21 October 2026

One token through 284 billion parameters

A 284-billion-parameter model runs on my laptop at about half a word per second, while its drive and its cores sit mostly idle. Follow one token through the model's 43 layers, switch between the engine builds I measured, and watch where the time goes.

01 · THE WORKLOAD

Six experts out of 256, 43 times

DeepSeek V4 Flash is a mixture of experts. At each of its 43 layers a small router picks 6 of 256 experts for the current token, so a token touches 258 experts: 3.45 GB of 4-bit weights. 64 GB of RAM cannot hold 167 GB, so colibri keeps the rest of the model in RAM and streams experts from the SSD. Popular experts stay cached: 37% of the experts in my runs were already in RAM (amber); the rest came from the drive (blue).

02 · THE DRIVE

The drive is not the limit

My storage benchmark reads expert-sized blocks at random with the OS cache bypassed: 4.8 GB/s with two to four reads in flight. During decoding the engine reads 0.72 GB/s. At full speed the drive alone would allow about 1.5 to 2 tokens per second, three to four times what the engine reaches.

03 · A CHAIN OF 43 STEPS

Cores busy a third of the time

Each router must finish before the engine knows which experts to load, so a token is a chain of 43 dependent load-then-compute steps. More threads made it faster, so compute is on the critical path, yet the cores were busy only about a third of the time. Watch the twelve thread lanes in the panel: most of each layer is waiting.

04 · THE MISSING INSTRUCTIONS

AVX-512 never runs

The Windows release is compiled for AVX2 with no runtime dispatch. In the shipped engine I counted 0 instructions on AVX-512 registers and 6,224 on AVX2 ones, so its AVX-512 4-bit kernel never runs. My own AVX-512 kernel does a token's 258 experts in 0.08 s on 12 cores. Rebuilt for Zen 5, the engine was 9% faster.

05 · THREADS THAT FALL ASLEEP

The big gap: 500 wake-ups a token

A second build with a different compiler and OpenMP runtime, same instruction set, was 50 to 55% faster. In GCC's OpenMP on Windows, threads waiting at a barrier go to sleep straight away; there is no spin loop, and the settings that ask for one have no effect there. colibri crosses about 500 barriers per token. LLVM's runtime spins instead: CPU use rises from 9% to 46%, and the waits disappear.

06 · THE CONTROL

Told to sleep, the fast build loses it all

One variable at a time: the fast build with OMP_WAIT_POLICY=passive fell back to the shipped engine's speed and CPU use. Asking the shipped engine to spin changed nothing. Wake-ups explain the whole gap, not the generated code. Every run wrote the same 24 tokens (same hash).

07 · WHAT IF

Let the drive set the pace

A projection, not a measurement: guess the next layer's experts from the current hidden state, load them while this layer computes, and cut the barriers to one per layer. Then the drive would set the pace, three to four times today's speed. These are the next experiments, and the panel marks this mode as a projection.

Method

How it was measured

  • A model of the workload from the model's config: bytes per token, expert sizes, what the cache saves.
  • A storage benchmark in C++20 that reads expert-sized blocks at random, bypassing the OS cache. Clean under ThreadSanitizer and AddressSanitizer.
  • An AVX-512 kernel for 4-bit weights that decodes 16 weights per permute instruction, checked against a scalar version on every run.
  • Profiled runs of the engine, and two engine builds from the same source, so one variable changes at a time.

In the panel, the order of the steps inside a layer comes from colibri's source. Their lengths are a model, scaled so each token takes the measured time. Which experts light up is random: the routing itself was not recorded.

I designed and directed this work; the code, builds and measurements were carried out by Claude Code running as my agent, with every change to a running system approved by me first.
