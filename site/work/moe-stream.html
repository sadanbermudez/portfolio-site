In plain words
Some AI models are made of many small parts, the experts, and use only a few for each word. I wrote a program that keeps those parts on the drive and loads each one when it is needed, with a limited amount of memory for the most useful ones. Then I measured how fast it writes with more or less memory and with different rules for what to keep.
Why it matters
Memory is the most expensive part of running AI. Knowing exactly how speed falls when a model does not fit, and which tricks win it back, decides what hardware a company needs to buy or whether a model can run on a laptop at all.
What I built
An inference engine in Python and PyTorch: the model split into 1,024 expert files, a cache with four policies, prefetching that guesses the next layer's experts, and reads that bypass the operating system's cache so the drive itself is measured. It is checked against the reference implementation before any number counts.
What I measured
All in memory: 8.6 word-pieces per second. Nothing cached: 1.0. Guessing the next experts early: +58%. With 8 GB of 13 GB in memory: 4.9, about 57% of full speed. The text was identical in every one of 27 conditions.
Glossary: the technical words on this page
Mixture of experts (MoE)
A model split into many small sub-networks, the experts. A router picks a few for each token: here 8 of 64 at each of 16 layers.
Token
A piece of text a model reads or writes, often part of a word. Speed is counted in tokens per second.
Offloading
Keeping part of a model outside memory, here on the SSD, and loading each piece when it is needed.
Cache
The experts kept in memory. A hit means the expert was already there; a miss means reading it from the drive.
LRU and LFU
Two rules for which expert to throw out when the cache is full: the least recently used, or the least frequently used.
Prefetch
Starting to read an expert before it is asked for, from a guess, so the read overlaps with computing.
Reference implementation
Hugging Face transformers' version of the same model, used as the ground truth for correctness.
bfloat16 and float32
Two ways to store numbers: 16 bits (fast, less precise) and 32 bits (exact enough to compare two programs bit for bit).

Findings

What the numbers say

  • The ceiling is compute. With every expert in memory the CPU writes 8.6 tokens per second. Everything below that is time waiting for the drive.
  • Prefetching pays at every size. Running the next layer's router on the current state guesses its experts early; 82% of the guesses are then used. With no cache at all, that alone is 58% faster.
  • The obvious rule fails on small caches. A token walks through 128 experts in a fixed order. When fewer than that fit, least-recently-used always throws out the one needed next: 1 GB of LRU got no hits at all. Least-frequently-used keeps the popular experts and got 26%.
  • A saved "hot set" does not transfer. The most-used experts, measured on a story prompt, did worse than LFU at every size on a technical question: routing depends on the text. colibri relies on exactly such a saved file, so its benefit depends on how similar the next prompt is to past use.
  • The drive is not yet the limit. Reads peaked at 3.1 GB/s with prefetch, against 4.8 GB/s measured for this SSD. More reads in flight is the next lever.

Correct first

Checked against the reference before any speed counts

A fast engine that writes different text is a bug, not a result. In 32-bit numbers, my engine and Hugging Face transformers give the same scores for every next word (largest difference 0.0000) and the same 48 words in a row. In 16-bit numbers the two drift apart at word 19, which is rounding order: the same sums added in a different order. Every one of the 27 conditions below produced exactly the same text, so caching and prefetching never change the answer.

Method

How it was built and measured

  • The model: OLMoE-1B-7B (AllenAI, fully open): 16 layers, 64 experts each, 8 per token; 6.9B parameters, 1.3B used per token.
  • The split: each of the 1,024 experts in its own 12.6 MB file, laid out so one read brings everything it needs.
  • Reads past the file cache: Windows keeps recently read files in memory, which would turn "reads from disk" into memory copies on a 64 GB laptop. Every read uses FILE_FLAG_NO_BUFFERING, so the SSD itself is measured.
  • The runs: 32 generated tokens per condition, the same prompt, and statistics counted over generated tokens only. The static hot set was calibrated on a different prompt. Every row records whether the laptop was on mains power before and after it; all 27 were. A first pass that crossed from battery to mains mid-run was discarded.

I designed and directed this work; the code and the runs were carried out by Claude Code running as my agent.
