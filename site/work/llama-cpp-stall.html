A 20x stall in llama.cpp's Vulkan backend

My voice assistant paused about 3 seconds before every answer. The model was fast; the delay was somewhere else. Eight measurements found it.

Voice, first word3.0 s → 0.7 s
One state snapshot0.61 s → 0.03 s
880 MB state read7,738 → 553 ms

Context

The model, Qwen3.6-35B-A3B, is a hybrid: part of it keeps a running state instead of a normal attention cache. To resume a conversation after its text changes, the server saves snapshots of that state, 63 MB each, two per request. On this laptop the GPU is integrated, so GPU and CPU share the same memory.

Diagnosis

8 steps

One measurement at a time

  1. Raw engine against the server. llama-bench read 16 prompt tokens in 0.11 s; the server took 1.4 to 2.5 s for the same work. The GPU kernels were not the problem.
  2. Settings ruled out. Batch size, context size and slot count on a separate test server changed nothing.
  3. Timestamped logs. Two snapshot saves of about 0.6 s each made up the whole delay.
  4. Snapshots off. Voice became 15 times faster, but the agent slowed to 21 s per turn. Reverted (below).
  5. Newer build, four Vulkan switches. No change, so the cost was in the code, not the configuration.
  6. A patch that failed. Skipping redundant GPU waits took a snapshot from 0.65 s to 0.61 s. Discarded.
  7. Timers on the read path. The waits took 14 ms in total. The CPU copy took 7,738 ms for 880 MB, about 114 MB/s: the memory is visible to the CPU but not cached by it.
  8. A one-condition fix. Read directly only from CPU-cached memory; otherwise let the GPU copy into a cached staging buffer first.
// ggml_vk_buffer_read_2d(): take the direct host read only when it is fast
if (src->memory_property_flags & vk::MemoryPropertyFlagBits::eHostVisible && src->device->uma &&

Verification

Same answers, word for word

  • The same scripted six-turn conversation at temperature 0 ran on the stock and fixed builds, in two modes: history resent verbatim, and history altered so the server must restore a snapshot.
  • Replies were identical word for word in both modes; snapshot restores 4 of 4 in each build.
  • The exact deployment, one library swapped, was rehearsed on a copy of the engine folder before production, with a backup and a one-step undo.

Outcome. After deploying, I found that the Vulkan backend's maintainer had merged the same fix two weeks earlier (llama.cpp #30049), prompted by a benchmark on the same GPU. My engine version predated it. This is an independent diagnosis, not an upstream contribution. I now check a file's recent history before patching it.

Reverted

The change that was faster and wrong

Turning snapshots off made voice answer in 0.5 s. An end-to-end test showed the agent re-reading its whole 13,700-token prompt every turn, 21 to 23 s instead of 3.5 s, so I restored the default 23 minutes later.

The voice client resends its own replies word for word, so its cache always matched. The agent re-formats its previous reply slightly, and a hybrid model cannot step its state back without a snapshot, so it started over every time. My first tests used only voice-style conversations; the full test of every service caught it. The decision, its numbers and what would change my mind are logged, so the trade-off is never re-made by accident.

Method

How it was built and tested

I designed and directed this work; the code, builds and measurements were carried out by Claude Code running as my agent, with every change to a running system approved by me first. I set the goals (faster voice and agent, no lost function, no cloud inference), chose the trade-offs, and decided what to deploy and when to revert.

  • Measure before and after on the production setup, with the same scripted requests.
  • Test risky changes on a separate server first.
  • Check behaviour, not only speed: deterministic output compared word for word.
  • Keep a backup and a one-step undo for every deployed change.
  • Record every decision and number, including the reverted change and the discarded patch.
